# Warhammer 40,000 Simulator (Java Edition)

Цифровой симулятор настольной игры Warhammer 40,000 (10-я редакция).
Проект реализует ядро правил (Core Rules), последовательность хода и механику боя в консольном режиме с архитектурой, готовой к подключению графического интерфейса (LibGDX).

## 🚀 Текущий статус: Рабочий прототип (v0.2)

Реализован полный игровой цикл (Game Loop) и математическая модель боя. Два игрока (Adeptus Custodes и World Eaters) могут сражаться в автоматизированном режиме с логами событий.

### ✅ Реализованные механики (Core Rules)
*   **Структура хода:**
    *   Автоматический менеджер хода (`TurnManager`).
    *   Смена фаз: Command -> Movement -> Shooting -> Charge -> Fight.
    *   Roll-off (бросок кубиков) за первый ход.
    *   Счетчик раундов и определение активного игрока.
*   **Боевая система (`CombatEngine`):**
    *   Полная последовательность атаки: **Hit Roll → Wound Roll → Save Roll → Damage**.
    *   **Hit Roll:** Учет BS/WS, модификаторов, Critical Hits (Natural 6) и промахов (Natural 1).
    *   **Wound Roll:** Таблица S vs T (2+, 3+, 4+, 5+, 6+), Critical Wounds.
    *   **Save Roll:** Выбор лучшего спасброска (Armor Save + AP vs Invulnerable Save).
    *   **Damage:** Переменный урон (D3, D6+X), распределение урона по моделям.
*   **Специальные правила (Keywords & Abilities):**
    *   **Devastating Wounds:** Игнорирование спасбросков при критическом ранении.
    *   **Feel No Pain 5+:** Способность игнорировать полученный урон.
    *   **Deep Strike:** Механика резервов (база).
*   **Фракционные способности:**
    *   **Martial Ka'tah (Adeptus Custodes):** Выбор боевой стойки (+1 Hit, +1 Wound или +1 Damage) в начале фазы.

### 💂 Реализованные Юниты
*   **Adeptus Custodes:**
    *   Trajann Valoris (Watcher's Axe, Eagle's Scream).
    *   Custodian Guard (Guardian Spear, Sentinel Blade, Misericordia).
*   **World Eaters:**
    *   Angron, Daemon Primarch (Samniarius & Spinegrinder - Strike/Sweep profiles).

## 🛠 Архитектура проекта
Проект построен на принципах ООП с четким разделением ответственности:
*   **Model:** `Datasheet`, `WeaponProfile` — неизменяемые данные (Stateless).
*   **State:** `UnitInstance` — живое состояние юнита (раны, модели, эффекты).
*   **Logic:** `CombatEngine`, `TurnManager` — чистая логика правил.
*   **Interfaces:** Система `Ability` позволяет легко добавлять новые правила без изменения движка.

## 📋 Требования

*   **JDK 21+** — используются switch expressions и другие современные возможности языка.
*   Консоль — бой выводится логом событий, а между раундами и при выборе боевой стойки требуется ввод с клавиатуры.

Внешних зависимостей нет: только стандартная библиотека Java. Системы сборки тоже нет — проект собирается средствами IDE или напрямую компилятором.

## ▶️ Запуск

**Через IDE (рекомендуется).** Открыть каталог проекта в IntelliJ IDEA, убедиться, что `src/main/java` помечен как Sources Root, и запустить класс `ru.smiras.warhammer40k.MainWarhammer40k`.

**Из консоли.** Скомпилировать все исходники в каталог `out` и запустить точку входа:

```bash
javac -d out $(find src/main/java -name "*.java")
java -cp out ru.smiras.warhammer40k.MainWarhammer40k
```

В PowerShell список файлов собирается иначе:

```powershell
javac -d out (Get-ChildItem -Recurse src/main/java -Filter *.java).FullName
java -cp out ru.smiras.warhammer40k.MainWarhammer40k
```

После запуска Adeptus Custodes и World Eaters сходятся в бою, а в консоль пишется пошаговый лог: чей ход, какая фаза, что выпало на кубиках и сколько ран прошло. Расчёт выполняется движком сам, но между шагами игра ждёт нажатия Enter, а в фазу команд просит выбрать боевую стойку — так лог успеваешь прочитать.

## 💡 Выводы

**Правила игры — идеальная задача для отработки полиморфизма.** В Warhammer сотни способностей, каждая из которых вмешивается в свой момент расчёта. Прописывать их условными операторами внутри движка означало бы получить нечитаемый метод на тысячу строк, который ломается при каждом добавлении. Интерфейс `Ability` с хуками на этапы атаки решает это: движок вызывает хуки, ничего не зная о конкретных правилах, а новое правило добавляется отдельным классом.

**Разделение неизменяемых данных и изменяемого состояния упрощает всё остальное.** `Datasheet` описывает, каким юнит создан, и никогда не меняется; `UnitInstance` хранит, что с ним стало в бою. Пока эти вещи лежали вместе, любое изменение состояния грозило испортить характеристики самого юнита.

**Урон оказался не числом, а поведением.** Попытка хранить его как `int` разбилась о профили вида «D6+2»: значение вычисляется в момент броска. Интерфейс с двумя реализациями — фиксированной и бросковой — убрал из движка все проверки «а это фиксированный урон или кубиковый».

**Главный урок — про тестируемость, и он получен на своей ошибке.** Случайность встроена в самую сердцевину игры, и я вызвал генератор броска напрямую из движка. Код работает, но проверить его нельзя: одни и те же входные данные дают разный результат. Правильное решение — отделить источник случайности от правил, которые её используют, и принимать его извне. Это и есть первый пункт плана выше.
